### <a name="_qmphm5d6rvi3"></a>**Решение**
В отдельных файлах приведены диаграммы контекста и контейнеров в модели C4. 

Для выполнения требований (2, 3) предлагается обеспечить балансировку запросов между инстансами интернет-банка, размещенными в двух ЦОД через Anycast и маршрутизацию по BGP. При этом используется Geo-binding по BGP. ЦОДы, в которых размещены сервисы, должны поддерживать Anycast, а провайдер Geo-binding по BGP (Ростелеком, Selectel).  

Внутри ЦОД реализован API Gateway, который маршрутизирует запросы на "старую" версию интернет-банка или микросервис обработки депозитов (14). 

Для разработки микросервиса выбран Java + Boot Spring, как технология уже использующаяся в кол центре (6) и  использующая экспертизу сотрудников с опытом в разработке на Java (7). 

Для хранения данных микросервиса используется PostgreSQL с логической репликацией шардированных данных. Шардирование данных должно быть согласовано со схемой Geo-binding, чтобы минимизировать пересылку данных между ЦОД в ходе выполнения транзакций. 

Все взаимодействия между сервисами и между клиентом и сервисами производятся с использованием TLS шифрования (11). Шифрование беспечивается настройкой site-to-site vpn на пограничных межсетевых экранах. 

Для исключения прямой работы сайта и интернет-банка с API АБС (только в части нового сервиса, старая часть остается как была) (15), снижения нагрузки на АБС и использования очереди сообщений (16) решено реализовать направление заявок на депозит в АБС, запросов на создание пользователей в интернет-банке и подтверждение выполнения этих действий через Kafka.

Требования по защите персональных данных должны быть выполнены в рамках отдельного проекта сотрудниками ИБ подразделения. Потребуется настройка TLS site-to-site vpn. Для этого предлагаемые технические решения по развитию системы должны быть согласованы с сотрудниками, отвечающими за ИБ и, при необходимости, должен быть иниицирован проект по перенастройке системы ИБ банка.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Опишите здесь наиболее важные альтернативные решения.
Рассматривался вариант балансировки нагрузки между ЦОД с использованием GSLB балансировщиков (Cloudflare - возникают задержки из-за удаленности и конфликты с блокировкой адресов РКН, Yandex Cloud Load Balancer - не поддерживает балансировку внешних IP, а реализация дополнительного proxy в Yandex Cloud усложняет, удорожает и не соответствует требованию минимальных задержек (4)).  

Рассматривался вариант применения уже используемых СУБД для "нового" интернет-банка (MS SQL или Oracle Database - невозможность официальной поставки, отсутствие поддержки от вендора). Рассматривался вариант использования Postgres Pro Enterprise с поддержкой Multimaster, что не требовало бы шардирования, но существенно дороже и требует введения рефери (признано нецелесообразным на этапе MVP).  

**Недостатки, ограничения, риски**

Используемая архитектура решения несет риск невыполнения требований по доступности (99,9%) с учетом отсутсвия резервирования АБС и сайта. На следующем после MVP этапе потребуется проработка этого вопроса.  

Возможность выполнения требования по минимальному времени отклика интернет-банка и конкретному его значению (200мс) должно быть проверено на этапе разработки MVP и, возможно, скорректировано. Также возможно, что потребуется внесение изменений в архитектуру интернет-банка.

Используемая схема распределения запросов (шардирование БД + Geo-binding BGP) требуют аккуратной настройки и поддержания в согласованном состоянии. При росте нагрузки будет необходимо перейти к Multimaster СУБД.

Необходимость привлечения ИБ подразделения усложняет, удорожает и замедляет реализацию проекта.
